# Triage

Sort each issue that reaches the tracker outside a plan graph until it ends with a **brief** an agent could build from, a specific question, a road for a new idea, or a reason to close it. The orchestrator runs it.

**Sorting starts nothing.** `ready-for-agent` means sorted and briefed, never approved. Work starts only when the user approves it (below).

## The work and the labels

Run `sh <triage-skill-folder>/find-work.sh` from the project's root. It prints one line per issue, oldest first: `#<n> new|to sort|reply|builder question: <title>`. It prints nothing and exits 0 when there is no work; exit 2 means it could not read everything (reason on stderr), never "nothing to do": run it again, and tell the user if it keeps failing. The list chooses what to read, never evidence: read each issue in full, every comment included. A `builder question` goes to "Answer a builder"; every other line to "Sort an issue". Change the script only with `python3 -I <triage-skill-folder>/test/test_find_work.py` passing.

Leave alone any issue with no state label that sits in a milestone, has a parent or has sub-issues: it is a spec or a planned ticket.

Every sorted issue ends with one category, `bug` or `enhancement`, and one state from `docs/agents/triage-labels.md` (if missing, run `setup` first; use its names): `needs-triage` (the user must evaluate), `needs-info` (waiting on someone's facts), `ready-for-agent`, `ready-for-human`, or `wontfix` (only after the user's yes, then close). A ticket being built keeps its labels: change only its `needs-info`. Two state labels on any other issue is a conflict: tell the user and change nothing.

Routine triage comments start with this line, exactly as Matt wrote it; approval records put their opening and pointer first, then a blank line and the marker:

```
> *This was generated by AI during triage.*
```

**Comments hold facts about the work:** no keys, tokens, personal details or thread ids. Follow `contracts/open-development.v1.md` when present: the user's exact words go in a private-repository comment; publicly give the decision in your own words, its date and that comment's pointer. If the private record cannot be saved or read back, stop and ask the orchestrator; never invent a pointer or post the words.

## Sort an issue

1. **Read** the whole issue, keeping what earlier triage settled; the glossary and ADRs (`docs/agents/domain.md`); for a low finding, its review and pull request. Search the default branch for the behaviour by what it does (**already built?**), and read every `.out-of-scope/` file when present (**rejected before?**, as [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) says). Done when you can say where you looked and both answers.
2. **Check the claim:** reproduce a bug, or run an outside pull request's tests, using only what the project lets you run without asking; for anything needing the user's machine, account or a live read, write down what it would take. Done with one result: **confirmed** (with its code path), **not reproduced**, or **not enough detail to try**.
3. **Decide and apply** one category and one state, removing the old state, and post the comment:

| You found | State | Comment |
| --- | --- | --- |
| Clear and checked; an agent can do it alone | `ready-for-agent` | A brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)) |
| It needs a person: judgement, access, a live step | `ready-for-human` | A brief with a **Why a person:** line |
| Facts someone can give are missing | `needs-info` | Triage notes (below) |
| A new idea that needs the user's design decisions | `needs-triage` | Its road from the project's `docs/agents/roads.md`: chat for small, `grill` then `to-spec` and `to-tickets` for medium, `wayfind` for very big. Ask the user; they pick |
| Already built, an earlier rejection, or you would reject it | `needs-triage` until the user's yes, then `wontfix` | Ask the user. On yes, say where it lives, or record it as [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) says, and close |

Done when the issue has one category and one state and its newest comment is yours, saying what you found and what happens next.

**Triage notes** keep everything settled and ask whoever can answer (the reporter, or the user when an agent filed it) specific questions, never "please provide more info":

```markdown
> *This was generated by AI during triage.*

## Triage notes

**What we know so far:**

- ...

**What we still need from <who can answer>:**

- ...
```

## Answer a builder

1. **Read** the question, its ticket, the spec, its grill, the glossary, the ADRs, `docs/agents/` and the code it asks about.
2. **If one of those settles it,** answer on the ticket with its source, remove `needs-info` and tell the builder in one line.
3. **If it needs a decision** none settles (design, a plan change, anything live), ask the user with your recommendation and say on the ticket it is with them. Save their exact answer as a private record and read it back, then post the decision in your own words, its date and the pointer. Remove `needs-info` only then.
4. **A file outside its owned paths:** add it only when no other open ticket owns it, recording the path and why on the ticket; otherwise ask the user.

Done when the ticket's newest comment is yours and `needs-info` is gone once answered.

## Nothing starts without approval

Work starts only when it joins a plan graph the user approves (`to-tickets`), or the user approves the issue on its own, naming it. Before asking, propose its owned paths and what it relies on, read fresh from the code. "Move #42 to `ready-for-agent`" changes a label: apply it and ask whether they also approve the work. Low findings wait for their spec's closing summary, each sorted with proposed paths first.

Record a standalone approval with the template below: the decision in your own words with no double quote marks, the pointer on the next line (a private issue or PR comment URL holding the exact answer, never a file link), the brief, owned paths and what it relies on.

### Record a batch decision

1. **On the spec issue,** name the approved and dropped issues in your own words, with the date and the private record pointer.
2. **On each approved follow-up's own issue,** post this record with the same private record pointer, linking the batch decision; `launch-fleet` reads approval only there:

```markdown
**Approved on its own by <user>, <YYYY-MM-DD>:** <decision>
Private record: <pointer>

> *This was generated by AI during triage.*

Batch decision: <batch decision URL>
Approved brief: <brief URL>
Owned paths: <owned paths>
Relies on: <what it relies on>
```

3. **Close each dropped follow-up as `wontfix`.** Unmentioned items get no record and keep waiting.

## Tell the user

Once per run, in your own thread, send only what needs them: a `wontfix` to confirm, a decision or road a `needs-triage` issue waits on, a question only they can answer, an approval, and each new `ready-for-human`. Give each the issue, what you found, the decision and your recommendation, worded so "yes" accepts it, and write it on the issue too (for a ticket, on its spec as well). When asked what needs attention, show `find-work.sh`'s list grouped by kind with counts. When the user names an issue, sort it now.

## Outside pull requests

When `docs/agents/issue-tracker.md` counts outside pull requests as requests, sort each as an issue with code attached, listed by `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER", "MEMBER", "COLLABORATOR") | not) | "#\(.number): \(.title)"'`. There `ready-for-agent` means an agent takes its next step; `ready-for-human` means it is ready for a person to merge.
