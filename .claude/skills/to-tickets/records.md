# Write and read back spec and graph decisions

A new plan is approved by its checks: the machine plan approval of
[to-tickets step 4](SKILL.md#4-approve-by-the-checks). This page covers the
records before it (J202): human-approved plans still in flight, their
requests, and approvals on their own.

Use [the publishing contract](../../contracts/open-development.v1.md) and
[decisions.v1](../../contracts/decisions.v1.md) with
[its schema](../../contracts/decisions.v1.schema.json). Only the orchestrator
writes these records. Resolve private routing from the project's settings
and verify private visibility before an exact reply is saved. Use the contract's
private subject or titled private record. Read back the exact answer and subject
before using its comment pointer. Public wording is a dated paraphrase with
the `Private record: <pointer>` line immediately under it.

## Requests

Send a public-safe metadata object on stdin to
`python3 -I "<to-tickets>/scripts/request.py"`.

- For spec confirmation, supply `id`, `risk`, `spec`, `summary` and `headline`.
  Use a repository-unique request ID, the qualified risk, the issue number,
  and the exact displayed summary and headline.
- For plan approval, also supply `tickets` from the complete issue read-back
  and pass `--revision revision.txt`, generated by a successful current
  `revision.sh` run. Copy the summary from the latest spec confirmation.
  Each ticket row supplies `number`, `title` and `blockers`.

The script prints one JSON fence for a separate spec comment or refuses with
a diagnostic. Check independent wording, risk and revision before posting.
An unknown risk disables answering. Live, release or publish needs its
additional confirmation. A valid JSON record grants no approval by itself.

Post using `gh issue comment <spec> --body-file <file>`. Read back the
GitHub comment ID, subject and complete body. On an uncertain write inspect
existing comments before retrying. Duplicate IDs, partial reads, changed
source or conflicting wording leave the request unresolved.

Only the orchestrator updates the JSON lifecycle by exact comment ID,
preserving the human comments. Supersede outdated wording before posting
a replacement. Resolve after the existing verified confirmation or approval.
A reply being sent, agreement plus a change, or an issue closing leaves the
request unresolved.

## Human records

For a spec:

```md
**Spec confirmed by <owner>, <YYYY-MM-DD>:** <decision>
Private record: <the verified private-comment URL>
```

For a graph:

````md
**Plan graph approved by <owner>, <YYYY-MM-DD>, revision <N>:** <decision>
Private record: <the verified private-comment URL>

Changed since revision <N-1>: <what changed>.

| Ticket | Title | Blocked by | Label |
| --- | --- | --- | --- |
<every read-back row with the label to apply>

Fingerprint: `<the SHA-256 of the revision text>`

<details><summary>Revision text</summary>

```text
<the revision text, exactly as revision.sh printed it>
```

</details>
`````

Omit the Changed since line at revision 1. Historical revision-v1 records need
new approval. The checker validates the latest record from the configured
record authors. Verify its fingerprint and private pointer independently.
Refusal leaves the graph gated.

For an approval on its own, such as a standing approval that applies to a
ticket outside a spec, use the same private read-back and public form:

```md
**Approved on its own by <owner>, <YYYY-MM-DD>:** <decision, naming the standing approval when used>
Private record: <the verified private-comment URL>

<the brief, owned paths and Relies on>
```
